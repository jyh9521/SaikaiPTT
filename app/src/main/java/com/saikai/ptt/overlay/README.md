# app.overlay

系统悬浮窗。绿色空闲 / 红色接收，显示远端用户名，点击打开应用。

**不持有通信状态。** `onReceivingChanged()` 由唯一那个监视会话状态机的地方
（`session.VoiceSessionCoordinator`）在**边沿**上推进来。这里不订阅会话、不询问会话、
除了当前屏幕上那个字符串之外不记住任何关于会话的事。这既是 Task36 的硬性要求，也是这个
窗口便宜的原因：一次通话它只变两次。

**一个窗口，且只在它能说出应用说不了的话时才存在。** 三个条件同时成立才显示：

1. 用户打开了开关（`overlay_enabled`）
2. 系统权限已授予（**每次 attach 都重新检查**——服务运行期间用户随时可以撤销）
3. **本应用没有任何界面在显示**

第三条值得解释：悬浮窗存在的意义是在应用不在前台时说明发生了什么。浮在自己的 Home 页
上面——那个页面本来就写着谁在讲话——等于同一句话在两处各说一遍，而且两处还会差一帧。

**通知是降级，不是并行。** `04_UI_UX §18.2` 规定悬浮窗在场时由悬浮窗负责。判断依据是
悬浮窗**实际**是否显示（`isShowing`），不是那个设置项：一个 attach 失败的窗口必须降级
到通知，而不是一起沉默。§18.2 唯一绝对禁止的是「没有任何可见反馈」。

**没有动画。** §19 允许有限时长的闪烁、禁止持续动画。这里两者都不做：开始接收时变一次
颜色和文字，结束时变回来。闪烁是为了吸引注意，而用户已经收到了一个响得多的提示——声音
正在从扬声器里放出来。本任务的验收标准是长时间后台运行不产生可观测 CPU，而这里除非会话
状态变化，否则不重绘。

**颜色不是唯一信号。** 空闲显示应用名、接收显示对方名字，文字本身就不同；圆点空闲是空心
环、接收是实心。灰度截图下两种状态依然可分（`§3`）。

**颜色取自 `res/values/colors.xml`，不取自 Compose 主题。** 这个包不允许 import
`com.saikai.ptt.ui`（`ArchitectureRulesTest`），而 View 也需要的是 int。两份拷贝由
`BrandColorsTest` 比对，漂移会让构建失败。

由 **Task36** 填充。
