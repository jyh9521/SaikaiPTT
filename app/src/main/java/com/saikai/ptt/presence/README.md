# app.presence

心跳与在线状态。广播心跳并携带忙线状态，维护 lastSeen 与超时判定。

与 `discovery` 严格分离：发现回答「有谁」，presence 回答「谁还在」。

由 **Task17** 填充。

## 已实现（Task17）

`UdpPresenceAnnouncer`：三个循环 + 一个 listener，payload 与 Discovery 共用。

- **每 5 秒广播一次**。广播而非逐 Peer 单播：N 台设备单播每周期产生 N×(N-1) 个包，
  广播只有 N 个。八台对讲机就是每 5 秒 56 个包对 8 个包，永远如此，且毫无收益。
- **每 2 秒扫一次超时**。超时是唯一背后没有数据包的状态跳转，必须有人主动去问。
- **忙线标志一变立刻补一次广播**。`peerState` 是第三方设备获知「对方在通话中」的
  唯一途径，等下一个周期意味着设备列表最长 5 秒是错的——而那正是用户在决定要不要
  按下说话的时刻。

**单次丢包不判离线**：WiFi 丢广播是常态，闪烁的列表比滞后的列表更糟。阈值是
3 个周期 + 1 秒容差。任何有效包（语音、PONG）都刷新存活——正在发音频的设备显然还在。

### 忙线 collector 为什么不用 `drop(1)`

显而易见的写法是丢掉第一个值（那是启动时的状态，Discovery 已经通告过）。那样有个洞：
如果忙线标志在 `start()` 与 collector 订阅之间翻转，StateFlow 会把**新值**作为第一个
发射值给出来，然后被当成旧值丢掉，忙线状态就要等到下一个周期才通告。

现在比较的是**实际发出去的值**（`announcedBusy`），不是「上一个发射值」。这是自愈的：
任何原因漏掉的一次通告，都会被下一次发射纠正。

副作用是启动时会立刻发一个心跳——这反而是好事：对端在 1 秒内变成 ONLINE，
而不是等 5 秒后的第一个周期。
