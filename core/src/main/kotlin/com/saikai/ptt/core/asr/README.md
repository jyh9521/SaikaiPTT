# core.asr

离线日语识别里**与引擎无关**的那一半：什么时候识别、识别几次、音频怎么变成样本。
引擎本身在 `app.asr`，因为它要链接原生库。

这个包由 **Task45** 建立，决策见 `docs/ADR/ADR-012-ASR-Reinstated.md`。

## 为什么要有这条边界

引擎已经换过一次了。`ADR-006` 选 Vosk，`ADR-011` 判它过不了 16 KB 页对齐，
`ADR-012` 改用 sherpa-onnx。那次更换之所以没伤到别的东西，是因为**没有任何一条
「什么时候识别」的规则写在引擎里面**。这个包就是那条边界，`CLAUDE.md §29` 的
interface-first 在这里不是形式主义。

`SpeechRecognizer` 只接受已经在本机的样本。`§18` 要求 100% 本地：没有云端 ASR、
不上传音频、没有远程 API。全应用唯一一次联网是下载模型，那是 Task46 的事，
不属于这个接口——它看不到网络。

## 重试次数记在内存里，这是故意的

`HistoryConfig.asrMaxRetries` 限制一条录音重试几次。这个计数只存在于
`TranscriptionQueue` 里，不落库。替代方案是给 `communication_record` 加一列，
而 Task45 明确不做 schema 变更——为一个只在进程存活期间有意义的数字做一次迁移、
将来改策略再做一次，代价太高。

**后果要说清楚，别等以后才发现**：一条录音失败两次之后进程被杀，回来时会重新
获得完整的重试额度。它落库的状态还是 PENDING，于是重新入队、重新算三次。

对手机上识别失败最常见的原因来说，这是对的行为——模型加载着的时候应用被系统
因内存杀掉。只有对一个永久无法解码的文件才是错的，代价是每次启动多烧几秒 CPU，
直到某一次尝试终于把 FAILED 写进去。

## 串行，而且语音优先

`next()` 一次只发一个，发出去的没报回来就不再发第二个。`ADR-012` 把识别耗时的
门槛定在「每秒音频不超过一秒 CPU」，而 `§18.3` 无条件把音频排在识别之上——
在一台 4 GB 的机器上同时跑两个识别器是这条规则的反面。

通话开始时正在等的那一条走 `defer()`：它**不计入重试次数**。识别根本没跑，
为此扣一次额度，等于让繁忙的一小时耗光一条录音的重试机会而它一次都没被真正试过。
`defer()` 放回队首，`failed()` 放回队尾——后者已经失败过，排在新录音后面。

## 解码链能在 JVM 上证明

`RecordingDecoder`：Ogg 容器（`core.audio.OggOpusReader`）→ Opus 帧
（接收路径已有的 `VoiceCodec`）→ 16 位 PCM → `-1.0..1.0` 的浮点。全程不重新编码
（`ADR-004 §6`）。

放在 `:core` 而不是 `:app`，是因为每一步都能在 JVM 上证明：配合
`PassthroughVoiceCodec`，**出来的样本就是进去的样本**。用真的 Opus 解码器时输出
只是「听起来差不多」，测试就只能断言「有东西出来了」——那和没测的区别不大。

缩放用除以 32768 而不是 32767：前者在二进制里是精确的，且让 `Short.MIN_VALUE`
正好落在 −1.0；后者会把它推出范围。

## 残缺的录音尽量救

容器层跳过校验和不过的页，解码层跳过编解码器拒绝的帧，两边都计数并上报。
`docs/05_DataModel.md §48` 的老规矩：能救多少救多少，半句话也比一个错误强。
上报是为了让「有洞的音频产出的字幕」能被标出来——`DecodedRecording.intact` 就是这个用途。
