# core.session

PTT 会话状态机：发送端 IDLE→REQUESTING→TRANSMITTING→ENDING，
接收端 IDLE→RECEIVING→ENDING，以及 INTERRUPTED 与各 FAILED 分支。

会话所有权的原子转移（Busy 与强插的仲裁）也在这里，
见 `docs/03_Protocol.md` §33、§34。

由 **Task19** 填充。

## 已实现（Task19）

| 文件 | 职责 |
|---|---|
| `SessionState.kt` | 单一密封状态 + 失败原因 + 会话结局 |
| `SessionSignals.kt` | 控制包发送的接缝（机器永远看不见 socket） |
| `VoiceAudio.kt` | 音频设备的接缝，四个方法，附 `NoVoiceAudio` |
| `SessionManager.kt` | 状态机本体 |

**一个变量，一把锁**。`SessionState` 就是 `03_Protocol §34` 说的那个「会话所有权」
变量，对它的每一次读写都在同一个 Mutex 内。关键在于：**判定与应答在同一个临界区**
——两台设备同时发 VOICE_START，绝不能都看到空闲、都被告知可以。这个类里其余的一切
都是从这一条推出来的。

**REQUESTING 不是 TRANSMITTING**。只有 VOICE_ACCEPT 能推进（§19.5：没有肯定应答时，
发送端状态机根本没有任何合法事件可以离开 REQUESTING）。采集在整个等待期间一直运行
并本地缓冲，所以这段等待对用户是免费的。

**由被叫方决定**。忙线与强插都是接收方的策略（§33）。呼叫方永远只发 VOICE_START
然后等结果，绝不去查设备列表自行判断——那份列表最长滞后一个心跳，判断出来是猜的。

### 三个容易写错的地方

1. **重发的 VOICE_START 必须再回一次 VOICE_ACCEPT，不能回 BUSY**。发送方最多重发两次；
   如果第一次的 VOICE_ACCEPT 丢了而我们回 BUSY，一个丢包就变成了一次被拒绝的通话。
2. **发送中不能套用 idle 超时**。发送期间对端什么都不回（设计上就没有确认包），
   套用 3 秒 idle 超时会掐掉每一条超过 3 秒的话音。idle 超时只作用于接收方；
   `maxDuration` 两端都管。
3. **立即失败与延迟失败严格分开**：本机自己能判定的失败（已在会话中 / 没有名字 /
   麦克风打不开 / 包发不出去）从 `requestTalk` 返回，**绝不**发到 `outcomes`；
   依赖对端的失败（BUSY / 无应答）只走 `outcomes`。两边都报会让每个调用方要么
   重复处理，要么二选一。

## 已实现（Task25）

| 文件 | 职责 |
|---|---|
| `DatagramSink.kt` | 发送管线与 socket 之间唯一的接缝 |
| `VoiceFrameBuffer.kt` | 等待应答期间捕获的帧，有界环形，满了丢最旧 |
| `VoiceRecording.kt` | 录音钩子的四个时刻，Task38 之前是 `NoVoiceRecording` |
| `VoiceTransmitter.kt` | 发送管线本体，同时也是状态机的 `SessionSignals` 实现 |

**发送管线放在 core，不放在 app**。它需要的东西——打包器、编解码器接口、配置——全在 core，
唯一属于平台的是「把这些字节发出去」，那就是 `DatagramSink`。这样「按下即录的音频是否按
捕获顺序发出」这类问题能在 JVM 上被断言，而不是靠两台手机在一个房间里试。

**`SessionSignals.voiceEnd` 去掉了两个参数**。VOICE_END 要带最后一帧的序号与帧数
（ADR-003 §4），而这两个数只有真正发出这些帧的对象知道：状态机不数帧，被编码器拒绝或被
socket 丢掉的帧从来没有变成过序号。从上面传下来只能是猜的——那正是这两个位置在发送管线
存在之前一直是 `0, 0` 的原因。

**一个 collector，不是四个订阅**。发送管线要知道对方何时接受、电源锁要知道会话是否存在、
前台服务类型要在讲话期间带上 `microphone`、UI 要看到状态。会话结束的路径有七条（松手、
BUSY、无应答、被强插、WiFi 掉线、来电抢焦点、服务停止），四个订阅就是四次漏掉其中一条的
机会，而漏掉留下的是一个没释放的 wake lock，或者一直亮着的麦克风指示灯。见
`app.session.VoiceSessionCoordinator`。

**每次发送新建编解码器**。`VoiceCodec` 在帧之间携带状态，而对端每接受一个会话都会新建
解码器；沿用上次发送的编码器等于用对端从未见过的历史做预测，而解错的恰恰是最前面几帧
——正是预滚缓冲要保护的那几帧。

## 已实现（Task26）

| 文件 | 职责 |
|---|---|
| `JitterBuffer.kt` | 排序、等待、放弃：决定下一帧是哪一帧，以及什么时候不再等 |
| `VoiceReceiver.kt` | 每场会话一个解码器，把上面那个决定变成声音 |

**没有定时器**。显而易见的做法是一个 20 ms 的 ticker 往外拉帧。这里一个都没有，因为
时钟本来就存在：`AudioTrack` 严格按实时消耗写进去的数据，所以「到达即写」自己就是节拍。
剩给缓冲区的只有**排序**，而排序完全可以由到达事件决定——「这一帧我等了多久」用
「又收到了几帧更新的」来度量，每秒 50 帧，一帧就是 20 ms。于是 `targetFrames = 3`
就是 60 ms 的等待，用缓冲区真正能观测到的单位表达，也不需要第二条线程去跟第一条对齐。

三个数字各自在管什么：

- **起播门限 3 帧**。整个缓冲区加进去的延迟只有这一次，60 ms，在 PRD 的端到端预算内。
  作用是让第一次乱序不必在零时间内解决。
- **目标深度 3 帧**。开播之后，缺的那一帧等到三帧更新的到齐就判丢。等更久能救回更多
  迟到包，代价是它后面的一切**永久**延后。
- **上限 10 帧**。再多就是攥着 200 ms 用户还没听到的音频，对讲机上这感觉就是坏了，
  哪怕每一帧最后都到了。丢**最旧**的——丢最新的会既留下延迟又丢掉音频。

溢出之后缓冲区不会一路补到最新，而是停在离最新三帧的位置继续等：那和对待迟到包是
同一条规则，结果是它重新落回目标深度，而不是被清空。

**丢帧按三个优先级填补**，这是 ADR-007「发现 2」留给本任务的决定：

1. **下一个包里的 FEC 冗余副本**（`decodeLost`）。ADR-004 开了 inband FEC，副本搭在
   **后一个**包里；缓冲区还握着后继帧时就能把真实音频取回来。不主动索取的话，那份
   FEC 码率就是白付的。
2. **编解码器自己的丢包隐藏**（`conceal`）。连后继帧也没了时用。代价和静音相同——
   解码器无论如何都要跨过这个洞推进状态。
3. **静音**，只在编解码器两样都做不到时。

`ADR-004 §4` 写的「插入静音帧」是在选定编解码器之前写的；静音现在是第三选择而不是
第一选择。`VoiceCodec` 因此新增 `conceal(out)`，默认返回 0（调用方补静音）。

## 已加固（Task27）

Task27 的大部分要求 Task12 与 Task26 已经满足，值得记下来而不是重做：乱序重排、
迟到丢弃、重复只处理一次都在 `JitterBuffer`；Session 与 Sender 不匹配在
`PacketValidator` 第 11 步，且按 §45 静默丢弃；语音帧从不重传。

真正补上的是三件事。

**一个能挂死接收线程的洞。** 原来的溢出处理是
`while (sequence - nextToPlay >= capacity) discardOldest()`。序号来自局域网上一台
只做过身份校验的设备；一个声称 `0x40000000` 的 VOICE_DATA 会让这个循环走二十亿步，
而它跑在语音接收线程上——那不会崩溃，只会让设备**再也收不到任何东西**。

现在两道防线：超过「一次会话最长时长所能容纳的帧数」的序号直接拒收（那不是跳变，
那是对端在说不可能的话，为它扔掉一缓冲区真实音频是错的）；余下的重同步**一次扫完
整个环**而不是每跳过一帧走一步，所以跳变的代价与跳多远无关。

**序号算术全部走 `SequenceNumbers.distance`**，不再裸写 `a - b`。行为没变——Int 减法
对任何小于 2^31 的真实距离本来就与 u32 计数器同样回绕——但 `a - b` 写在两个序号之间
看上去正是 `isNewer` 要防的那个 bug，而「每处都写清楚再加个注释」的下场是总有一处
没加注释。测试把缓冲区一路推过 2^31 边界，验证过界后照常播放。

**`flush` 只播到实际收到的最新帧**，不再以对端声称的 `finalDataSequence` 为终点。
帧数是个计数，不是「在这里停」的指令：以它为准，一个说谎的或损坏的 VOICE_END 就能
悄悄切掉一段完整到达的音频。差值改为纯诊断——`neverArrived`。

`ReceptionStats` 把一次接收的结果拆成五个数（播放/补帧/迟到/太迟丢弃/从未到达），
分开是因为它们对网络的含义不同：`droppedOverflow` 是链路先卡后追，听感最差；
`droppedImplausible` 永远应该是 0，非 0 意味着有对端在发不可能属于该会话的序号。
