# core.history

历史记录的**清理**。读写记录本身在 `core.domain.HistoryRepository`
与 `app.storage.history`，这里只放一件事：什么时候可以删、按什么顺序删。

单独成包，因为这是全应用唯一一处**删除用户拿不回来的东西**的代码。它值得自己的
测试、自己的抽象、自己的一段说明。

## 顺序不是风格问题

`05_DataModel §30`：

```text
查过期记录 → 删音频 → 删数据库行 → 扫孤立文件
```

两个存储不可能放进同一个事务，所以顺序决定了「中途死掉」时坏成什么样。
**先删行再死** = 留下一个谁都不再引用的文件，而孤立扫描只在一次成功的 pass 之后
才跑，于是它永远不会被发现。**先删文件再死** = 留下一条音频缺失的记录，而详情页
本来就处理这种情况（Task39：照常显示其余信息，播放按钮带理由禁用）。
一个是泄漏，一个是已经写好的界面。

## 单个失败不中止整轮

同样是 §30。一个删不掉的文件只记一行日志，**并且保留它的数据库行**——否则下一轮
孤立扫描会看到一个没有记录的文件，把它当孤儿删掉，而那条记录已经先没了。
保留行意味着下一轮会重新试这个文件。

数据库读不出来则整轮停止，包括跳过孤立扫描：读不出来时「被引用的路径」是空集，
扫描会把设备上每一个录音都当成孤儿。这是这里最危险的失败模式，所以它被显式挡住，
并有测试钉住。

## 收藏永不自动清理

`§25`。规则写在查询里（`HistoryRepository.expiredBefore`），不写在 cleaner 里，
这样没有任何调用方能忘掉它。收藏的音频也自动受保护：它被行引用着，孤立扫描不会碰。

## 「正在使用」怎么判断

`§31` 列了三种不能删的情况，这里用两条规则覆盖：

| 情况 | 靠什么识别 |
|---|---|
| 正在录音 | 路径在 `records/.tmp/` 下（`§32`），且被 `ActiveRecordings` 认领 |
| 正在播放 | 被 `ActiveRecordings` 认领 |
| 正在进行的 PTT | 同「正在录音」 |
| 刚写完、行还没插进去 | **年龄**——不到一小时的无引用文件不算孤儿 |

最后一条是前两条覆盖不到的缝：文件已经关闭、移走、没人认领、也还没有行指向它，
这个窗口只有几毫秒宽。宽限期给到一小时，因为判断错的代价是删掉用户刚说完的一段话，
而等待的代价是一小时的磁盘占用——反正它本来就要被删。

`ActiveRecordings` 用**计数**而不是标志位，这样两个持有者按任意顺序释放都是安全的，
并且提供 `holding {}`：认领泄漏一次，那个文件就再也清理不掉了。

由 **Task40** 建立。
